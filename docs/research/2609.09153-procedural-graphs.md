## 1. TL;DR

- The paper's core idea is a typed, attributed **procedural graph**:
  `(procedure, relation, procedure)` triplets, mirroring a knowledge graph but
  for "what to do" instead of "what is." Edges carry three textual attributes —
  `condition`, `guidance`, `pitfalls` — and the relation vocabulary used across
  all their benchmarks is exactly four types: `LEADS_TO`, `TRIGGERS`,
  `PROVIDES_INPUT_FOR`, `CONVERGES_TO`.
- At inference time a **guidance LLM** (`Ψ`) localizes the agent's current node,
  pulls its 2-hop neighborhood, and *generates* situational advice from the
  edge attributes — a soft bias appended to the solver's prompt, not a hard
  constraint on legal actions.
- Offline, an **LLM refiner** contrasts high- vs low-scoring training
  trajectories, proposes add/delete edits to topology and attributes, and a
  candidate is committed only if it matches or beats the *current* graph's
  score on an independent held-out validation set (ties count as accept).
  Rejected candidates are logged and fed back to the refiner as negative
  evidence (rejection memory) — this whole loop runs with **no human review
  step**.
- Across 7 benchmarks, 4 LLM backbones (Claude Sonnet 4.6, Gemini 3.1 Pro,
  Gemini 3.5 Flash, Grok 4.1 Fast) and 7 baselines (Vanilla ReAct, MemoryBank,
  RAP, ExpeL, AutoGuide, AWM, KnowAgent), Procedural Graph wins or ties in
  21/24 model×benchmark settings and self-evolution from a minimal skeleton
  matches or beats a hand-designed graph — and can *repair* a bad hand-written
  prior (MultiChallenge: expert prior 87.50% → 58.93% success after adoption,
  recovered to 92.86% by the evolution loop).
- **agenticgraphs has no equivalent of any of the three load-bearing
  mechanisms**: no typed procedural-relation vocabulary on edges (AGR edges
  carry only `from`/`to`/`when`/`kind: flow|error|compensate` —
  `spec/agr-graph.schema.json`), no generative per-step guidance model (the
  runtime hands a node only `f"You are node '{id}' (speciality: {...}) in a
  workflow."` — `docs/architecture-m11.md` §1.4), and no trajectory-contrasting,
  validation-gated LLM refiner (`agr optimize` is "a v0 deterministic
  hill-climb over safe structural operators" — three fixed, non-learned
  operators — `src/agenticgraphs/mutate.py` lines 1-6, 131-210).
- Where agenticgraphs *is* strong — arguably stronger than the paper's
  Algorithm 1 — is in **structural gating and evidence discipline**: MAST lint,
  schema validation, provenance checks, a graded evidence ladder
  (`describe-only < assert-fixture < assert-live < assert-grounded < command`),
  and an autonomy model that commits unattended mutations only to an isolated
  `auto/mutations` branch that is never pushed and never touches `main`
  (`docs/autonomy.md`). The paper's loop has no such isolation — a committed
  graph *is* the new production graph.
- The single graph in the registry that structurally resembles the paper's
  mechanism — `graphs/research-knowledge/prompt-graph-optimization/graph.yaml`
  (baseline → beam-search → held-out-confirm) — searches *externally supplied*
  variants of some other graph, not the registry's own topology, and is not
  how any of the 83 shipped graphs actually got built.

## 2. Paper summary

### 2.1 Problem

Most LLM agents (the paper frames this against ReAct and its descendants)
select actions by unconstrained generation over a growing, flat trajectory log.
The paper's diagnosis: this leaves "what to do, in what order, under what
conditions" implicit, and as trajectories lengthen agents "lose track of their
objectives, invoke tools out of order, and repeat unproductive actions."
Existing structure-providing approaches are placed on a spectrum: free-text
memory/self-reflection (Reflexion, ExpeL) preserves experience but doesn't
connect steps; state-conditioned guidelines (AutoGuide) retrieve targeted
advice but not the surrounding procedural dependencies; hand-built workflows/
state machines (FlowBench, KnowAgent) make steps explicit but require manual
design; automated workflow search (AFlow) reduces manual effort but is offline
and doesn't condition guidance on the agent's live progress. The paper frames
its contribution as closing the gap: "an editable procedure representation
with guidance that is conditioned on the agent's current progress."

### 2.2 Method — the two phases

**Formal representation** (§3.1): `G = (V, R, E, Φ)`, `E ⊆ V × R × V`. `V` is
abstract nodes (tool calls, reasoning steps, or task states); `R` is the
relation vocabulary; each edge `(u, r, v)` states `v` is admissible after `u`
under relation `r`; `Φ` maps each edge to a schema-defined attribute set — in
their implementation, three textual fields: `condition` (when the transition
applies), `guidance` (how to proceed), `pitfalls` (what to avoid). Example
quoted verbatim from the paper: a financial-planning edge
`(cash_flow_forecast, LEADS_TO, fund_raising_request)` carries `condition:
projected runway falls below the safety buffer`, `guidance: submit the
request early to allow for the financing delivery delay`, `pitfalls: do not
stack a second request while one is pending`.

**Online inference — Generative Guidance** (§3.2): at decision step `t`, the
agent's active node `u_t` is localized by exact string match of the most
recent tool call to a node id (`Match(a_{t-1}, V)`); if matching succeeds, the
directed neighborhood `N_h(u_t)` is extracted (the node plus outgoing
transitions up to `h` hops); if matching fails, the *full graph* `G` is used
as fallback. A guidance LLM `Ψ` reads this neighborhood plus the last `w`
trajectory steps and generates situational guidance `g_t`, which is appended
to the solver's prompt: `a_t ~ P_solver(· | q, T_t, g_t)`. The paper is
explicit that this is a **soft bias, not a hard constraint** — the solver can
still deviate. Default configuration across all experiments: `h=2`, `w=3`.

**Offline self-evolution** (§3.3, Algorithm 1): a four-step loop run for `K`
rounds, each starting from the *retained* graph of the previous round (a
rejected candidate never becomes next round's starting point):
1. **Diagnostic rollout** — run the retained graph on a training batch,
   record trajectories + scores.
2. **Feedback-driven mutation** — an LLM refiner (same backbone as solver)
   contrasts high- vs low-scoring traces (successes vs failures for binary
   tasks) and emits a structured edit set: `Add` (missing verification
   nodes/edges) and `Delete` (nodes/edges that repeatedly cause failure or
   block progress). Attribute revision is implemented as delete-then-re-add
   with new attribute values.
3. **Validation gating** — the candidate `G_k^cand = G_{k-1} ⊕ ΔG_k` must
   first pass structural checks (valid edge endpoints, a directed path from
   every node to a zero-out-degree terminal node, optional cycle repair
   depending on a configured cycle policy). Structurally invalid candidates
   never reach validation rollout. Valid candidates are scored on an
   independent held-out set `D_val`; the retained graph updates only if
   `S_val(G_k^cand) ≥ S_val(G_{k-1})` — **ties are accepted**, which the paper
   states explicitly (Eq. 5, and Algorithm 1 line 16: `if S_k^cand ≥ S_{k-1}`).
4. **Rejection memory** — rejected candidates (structural failures *and*
   validation losses) are logged with their trajectories and outcomes into
   `H_rejected`, which is serialized and given to the refiner as negative
   evidence on the next round, to discourage repeating the same failed edit.

Note on validity enforcement: the paper is explicit that matching
action-node names to the available tool catalog is a **refiner-prompt
requirement** (rule 1 in the refiner prompt, Appendix B.5), not something the
"generic structural validator" independently checks (Appendix B.6). This is a
soft constraint inside the loop, not a hard gate.

### 2.3 Evaluation

**Benchmarks (7):** HotpotQA (multi-hop QA w/ search tools), MultiChallenge
(instruction retention across multi-turn dialogue), GDPval (open-ended
professional tasks scored against expert rubrics), ALFWorld (embodied
household tasks, strict action ordering), τ-bench (policy-compliant tool use
under live user interaction, retail domain), BFCL v3 (multi-turn function
calling), EnterpriseArena (long-horizon financial/CFO simulation under
delayed feedback and scheduled macroeconomic crises).

**Backbones (4):** Claude Sonnet 4.6, Gemini 3.1 Pro, Gemini 3.5 Flash, Grok
4.1 Fast. Guidance model and offline refiner always share the solver's
backbone. All calls use greedy decoding (temperature 0).

**Baselines (7), all sharing the identical ReAct solver and identical
training trajectories as PG's self-evolution:** Vanilla ReAct (no memory),
MemoryBank (summarized experience w/ forgetting), RAP (retrieved trajectory
exemplars), ExpeL (distilled natural-language insights from
success/failure contrast), AutoGuide (state-conditioned guidelines,
"closest" prior work per the paper's own related-work framing), AWM (induced
linear workflows), KnowAgent (textual action-transition rules).

**Graph statistics (Appendix B.4, Table 7):** compact everywhere except BFCL
v3 — HotpotQA 9 nodes/9 triplets, MultiChallenge 7/7, GDPval 15/22, ALFWorld
11/27, τ-bench 17/18, EnterpriseArena 11/13, BFCL v3 131 nodes/265 triplets
(mirrors its large function catalog). Relation vocabulary across **all**
graphs: `LEADS_TO`, `TRIGGERS`, `PROVIDES_INPUT_FOR`, `CONVERGES_TO` — four
types total, no per-benchmark customization mentioned.

### 2.4 Results (numbers quoted verbatim from the tables)

**Main results (Table 1, 4 models × 6 benchmarks = 24 settings):** PG ranks
first or joint-first in 21/24 settings; vs. the strongest baseline per
setting, 19 wins / 2 ties / 3 losses (one-sided exact binomial sign test
excluding ties, p = 4.3×10⁻⁴). Largest margins: BFCL v3 + Gemini 3.5 Flash
67.00% vs. 58.00% (+9.00 pts); GDPval + Gemini 3.1 Pro 78.78 vs. 71.37 (+7.41);
τ-bench + Gemini 3.1 Pro 80.00% vs. 73.04% (+6.96). Weakest/most mixed
benchmark: HotpotQA, where margins over the strongest baseline range from
−0.90 to +1.30 points — i.e. PG can *lose* here (e.g., Claude Sonnet 4.6:
74.50 PG vs. 75.40 AutoGuide).

**EnterpriseArena / long-horizon resilience (§5.2, Table 8):** full-horizon
survival rises from 44.0%→58.0% (Claude Sonnet 4.6), 6.0%→34.0% (Gemini 3.1
Pro), 26.0%→40.0% (Grok 4.1 Fast). On Gemini 3.5 Flash, **all four
configurations (baseline, RAP, MemoryBank, PG) reach 0.0% full-horizon
survival**; PG still raises mean lifespan (33.58→40.62 months) and average
capital raised ($0.00M baseline vs. $9.39M PG). Tool-call efficiency is
model-dependent, not uniformly reduced: PG cuts Gemini 3.5 Flash's tool calls
per month from 18.94→12.53, but *increases* them for Claude Sonnet 4.6
(0.13→0.36) and Gemini 3.1 Pro (0.89→3.18) — the paper's own reading is that
guidance changes *which* tools are called and *when*, not simply *how many*.

**Construction-strategy ablation (§5.3, Table 2, HotpotQA + MultiChallenge,
5 modes vs. unguided baseline):** Mode 5 (scratch-initialized + online
evolution) is best on HotpotQA (66.30 EM / 78.79 F1, +7.50/+7.58 over
baseline). On MultiChallenge, Mode 3 (expert-initialized + online evolution)
tops at 92.86% overall success, Mode 5 close behind at 91.07% — **both
beating the unguided baseline's 87.50%**, while the hand-crafted expert graph
used *without* evolution (Mode 1) *underperforms* the unguided baseline
(58.93% vs. 87.50%), and a single non-iterative offline update on top of that
expert graph (Mode 2) makes it *worse still* (53.57%). Only the iterative,
validation-gated loop (Mode 3) recovers — to 92.86%, a 33.93-point gain over
the expert starting point.

**Self-evolution rounds on EnterpriseArena (§5.4, Table 11, 10 rounds):**
validation-split baseline is 0.0% full-horizon survival / 34.8 months mean
lifespan. Round 1 discovers a sequential audit→forecast→decide backbone,
jumping validation survival to 45.0%. Round 2 adds a `recall_notes` node
(external working memory across months), reaching 80.0% validation survival
while cutting tool calls/month from 17.23 (baseline) to 3.08. Rounds 3, 4, 6
are proposed and **rolled back** by the validation gate (e.g., Round 3 lowered
a fundraising threshold, worked on training seeds, cost 15 validation-survival
points and was rejected). Round 5's candidate fails structural verification
before it even reaches rollout. Round 7 prunes a no-op `pass_action` branch
(80.0% held). Round 8 replaces a `fund_raising_request→book_closing` edge
with a direct edge to `End` ("administrative bypass"), reaching 90.0%. Round
9 is flat. Round 10 is rejected (training 90.0% but validation dropped to
85.0%) and the loop terminates, **returning the Round 9 graph**. Test-set
result for the *returned* graph: 85.0% survival vs. baseline's 0.0% (Fisher's
exact p = 2.6×10⁻⁸); the paper explicitly notes the *best single round
observed* during the search reached 95.0% but they report the returned graph
instead, "since quoting the latter would amount to selecting on the test
set" — a methodological point worth flagging as a genuine discipline the
paper practices.

**Efficiency ablation (§5.5, Table 3, Gemini 3.5 Flash):** localized subgraph
+ generative guidance beats full-graph raw injection and full-graph
generative guidance on all three benchmarks tested (MultiChallenge 89.31 vs.
86.60/87.35/80.27-baseline; GDPval 63.99 vs. 57.17/56.75/54.80; ALFWorld
81.53 vs. 70.34/**54.48**/72.58). Full-graph *generative* guidance actively
hurts ALFWorld (72.58 baseline → 54.48) while ballooning average tokens per
sample to 96,360 (vs. 28,064 for the localized/generative configuration the
paper ships). The paper's own framing: "guidance increases token use even
when it reduces solver steps."

### 2.5 What the paper does *not* provide (checked against retrieved text)

- **No explicit "Limitations" section.** Caveats are distributed across the
  Conclusion (token overhead vs. step reduction; open question of guidance
  reuse/selective generation; untested transfer across solvers/tool
  interfaces) and inline discussion (e.g. HotpotQA's negative-margin cases,
  Gemini 3.5 Flash's 0% EnterpriseArena survival under every configuration).
- **No stated code/data release URL** in the retrieved text (abstract, full
  PDF body, references, appendices A–F).
- **No cost/latency-in-dollars figures** — only token counts and wall-clock
  latency in seconds (Appendix D.1, Tables 9–10).
- **No human evaluation / user study** — not stated in retrieved sources.
- **No ablation on the number of relation types** (i.e., whether 4 relation
  types is load-bearing vs. an unconstrained-label design choice) — not
  stated in retrieved sources; the paper only reports that these four are the
  ones that occur in their constructed graphs, not that the vocabulary is
  fixed or validated as complete.

## 3. Mechanism deep-dive

### 3.1 The triplet representation is genuinely a graph, not a rule list

The key structural claim (implicit in the paper's framing against AutoGuide,
its self-identified closest prior work) is that **connectivity matters**: "For
example, retrieving guidance for `submit` without the preceding
`check_answer` transition can omit the verification step that makes
submission appropriate." AutoGuide retrieves state-matched guidelines
independently per state; PG retrieves a *connected neighborhood*, so a step's
guidance is generated with awareness of both what came before it and what
follows. This is the concrete mechanism behind the efficiency ablation
result in §2.4 above (Table 3): localization to the graph neighborhood, not
mere access to more text, is what drives PG's advantage — full-graph access
(more information, less structure per step) performs worse than the localized
version on 2 of 3 benchmarks tested.

### 3.2 Guidance is generated, not retrieved verbatim, and is explicitly a bias

Equation 3 in the paper (`a_t ~ P_solver(· | q, T_t, g_t)`) is a standard
conditional-generation formulation — `g_t` is just more context, with no
mechanism forcing the solver to obey it. The paper calls this "soft
integration": the agent "maintain[s] flexible reasoning while being steered."
This is a deliberate design choice, contrasted explicitly against hard
constrained-decoding approaches (the paper cites TOOLDEC/Outlines in related
work as guaranteeing syntactic validity but saying "nothing about whether an
action is semantically admissible given the task state").

### 3.3 The validation-gated refiner loop is the paper's real novelty

Three properties make this loop distinct from ordinary offline
hyperparameter search:
1. **Contrastive input** — the refiner sees both successful and failed
   trajectories from the *same* round, not just failures, and Appendix E.3's
   topological trace shows it acting on both signals (adding a note-recall
   node because successful runs used ad hoc memory; pruning a no-op branch
   because failed runs used it as an escape hatch).
2. **Strict non-regression on an independent split, with ties accepted** —
   `S_val(cand) ≥ S_val(current)`. This means the loop is monotonic *on the
   validation set by construction* (never accepts something measured worse),
   but the paper is careful to show this doesn't fully protect the test set:
   Round 10 in the EnterpriseArena trace shows training-set improvement
   (90.0%) that did *not* generalize to validation (85.0%, a regression) — the
   gate caught it. The paper explicitly cautions that with only 20 validation
   episodes per split, "individual accept/reject decisions turn on one or two
   episodes and should be read as a search trace rather than as significance
   tests" — a genuinely honest caveat about the statistical power of the gate
   itself.
3. **Rejection memory as an explicit negative-example channel** — not just
   "don't repeat this," but the rejected candidate graph, its edits, its
   training trajectories, and its validation outcome are all serialized back
   into the refiner's next-round context. This is closer to a rudimentary
   in-context reinforcement signal than to standard early-stopping.

Everything in this loop happens **without a human in it**. Algorithm 1 has no
step for human review, sign-off, or override — acceptance is purely
`S_val(cand) ≥ S_val(current)`. This is the single most important structural
fact to carry into the agenticgraphs comparison in §5 below.

## 4. Where agenticgraphs already agrees

- **Graphs as the unit of procedural knowledge, kept outside model weights,
  inspectable and editable without retraining** — this is agenticgraphs'
  entire premise. `README.md` §"About The Project": "A registry of ready-made
  multi-agent workflow graphs in a portable, framework-neutral format," with
  `graphs/<domain>/<name>/graph.yaml` as the authored unit
  (README `### Concepts` table). Matches the paper's framing of PG as
  "explicit and editable... outside the model weights."

- **Nodes as abstracted roles/actions, not raw tool calls.** The paper's `V`
  "abstracts a tool function, a skill, an internal reasoning step, or a task
  status" (§3.1). AGR nodes carry a `speciality` (role, e.g.
  `security-auditor`) plus `abilities` (bindable atomic capabilities) —
  `spec/agr-ability.schema.json`, `specialities/researcher.yaml` (example:
  `requires_abilities: [web_search]`). Conceptually the same abstraction
  layer — a node is a role with capabilities, not a literal function
  signature.

- **Structural validity as a precondition for any mutation to count.** The
  paper's Algorithm 1 `PrepareCandidate` step requires valid edge endpoints
  and a directed path from every node to a zero-out-degree terminal before a
  candidate is even scored (§3.3, Appendix B.6). agenticgraphs' `agr
  validate` (schema conformance + MAST lint: dangling edges, unreachable
  nodes, unbounded back-edges, verifier-free termination — README
  "Contributing" section) enforces the same category of property, and
  arguably more of it (README `### 🧭 About The Project`: "the schema
  rejects any graph whose verifier is missing, whose loop has no exit
  condition, or whose node claims a speciality it lacks the abilities for").
  Every mutation path — `agr infuse`, `agr optimize --apply`, MCP
  `infuse_ability(persist=true)` — is required to pass this gate before
  anything is written (`docs/autonomy.md` §"The gate, unchanged"; enforced in
  code by `_write_checked` in `src/agenticgraphs/mutate.py` lines 31-36,
  which writes, re-validates, and **rolls back to the original file on any
  validation error**).

- **Held-out evaluation as the thing that actually counts, not self-report.**
  The paper's `S_val` is a genuine score computed by re-running the candidate
  on data the round's training batch never touched. agenticgraphs' entire
  "quality is measured not claimed" principle (README top-of-file
  `principles:` block) and its `profile.json` `measured` /
  `measured_live` split — see
  `graphs/research-knowledge/prompt-graph-optimization/profile.json` lines
  17-58 (mock, provisional) vs. 59-224 (real-model recordings, per-model pass
  rate, `models_disagree` flag) — is the same underlying instinct: a claim
  that isn't backed by an actual re-run doesn't count.

- **A held-out-gated search motif exists in the registry, structurally
  matching the paper's shape (if not its subject).**
  `graphs/research-knowledge/prompt-graph-optimization/graph.yaml`: `baseline`
  (evaluator, scores the input graph) → `search` (`kind: search`,
  `search: {branch: 3, depth: 3, prune: beam(2), objective: max}`) →
  `confirm` (`kind: verifier`, `criteria: "A variant ships only if it beats
  the baseline on a held-out set it was never searched against. A winner
  selected on the set that selected it has measured its own search, not its
  quality."`). Its `termination.contract` and `verification.assert
  (output.holdout_score > output.baseline_score)` are, almost verbatim, the
  paper's validation-gate inequality (Eq. 5). This is the closest single
  artifact in the registry to "what the paper's Algorithm 1 does," and it is
  worth noting explicitly in any pitch that agenticgraphs "gets" the
  held-out-gating idea in principle — it just isn't how the registry mutates
  *itself*.

- **A rejection/lineage log exists, in weaker form.** The paper's
  `H_rejected` (rejected candidates + trajectories + outcomes, replayed to
  the refiner) has a structural cousin in AGR's `lineage.yaml` sidecar
  (`docs/autonomy.md` §"The gate, unchanged" item 3; example at
  `graphs/software-engineering/code-review-pipeline/lineage.yaml`, an
  append-only log of accepted `infuse`/`optimize` operations with
  timestamps). It differs in one important way — see §5.

- **A generative, per-node text field the paper would recognize.** AGR v1.8's
  `criteria` field on `kind: verifier` nodes (`docs/agr-v1.8.md` §"`criteria`
  — the rubric") is free-form prose describing "what the claim means in this
  domain," carried into every emitted LangGraph/CrewAI/AutoGen stub. This is
  structurally closer to the paper's edge `condition`/`guidance`/`pitfalls`
  triplet than anything else in AGR — both are natural-language fields
  attached to the graph artifact that are meant to reach the model at
  runtime, not just document intent for a human reader. The scope differs
  sharply (see §5.1).

## 5. Where agenticgraphs differs / is missing

### 5.1 No typed procedural-relation vocabulary on edges

The paper's whole framing device — "just as a knowledge graph organizes
facts into `(entity, relation, entity)` triplets... a Procedural Graph
organizes procedural information into `(procedure, relation, procedure)`
triplets" — has no counterpart in AGR. Checked directly against
`spec/agr-graph.schema.json`: an edge has exactly `from`, `to`, an optional
`when` (a free-text boolean guard string, evaluated through a restricted
expression allowlist — `src/agenticgraphs/safeexpr.py`, not a semantic
relation), and `kind` constrained to `{flow, error, compensate}` — a
*structural* classification of the edge's role in the control-flow graph
(normal path / failure path / undo path), not a *semantic* relation between
two procedures the way `LEADS_TO`/`TRIGGERS`/`PROVIDES_INPUT_FOR`/
`CONVERGES_TO` are. There is no edge-level `condition`, `guidance`, or
`pitfalls` attribute anywhere in the schema — `docs/agr-v1.8.md` confirms the
only new prose field this version added is `criteria`, and it is scoped to
`kind: verifier` **nodes**, not to edges, and it is a grading rubric ("what
checks a claim"), not step-level "how to proceed" advice. An AGR graph
literally cannot express "node A leads to node B under condition X, here is
how, here is what to avoid" as a first-class, schema-validated artifact
today.

### 5.2 No generative guidance model at inference time — none at all

This is the largest single gap, and it is directly evidenced by
`docs/architecture-m11.md` §1.4 ("The finding that changes the second
question"): the current runtime sends a node **exactly one** string —
`f"You are node '{id}' (speciality: {node['speciality']}) in a workflow."` —
and nothing else. Specifically documented as zero: `prompt_seed` (declared in
the speciality schema since M0) is read by **0 lines of runtime code**;
speciality YAML files (`researcher.yaml`'s description — "Gathers and grounds
facts from sources" — is the architecture doc's own example) are "never
opened during a run." There is no local-subgraph extraction, no 2-hop
neighborhood walk, no separate guidance-generation LLM call, no localization
of an "active node" from the trajectory the way the paper's `Match(a_{t-1},
V)` does. `LLMRunner` (per `docs/evidence-history.md`) "sends a prompt and
parses JSON; that is all it does." The paper's entire §3.2 mechanism —
locate → extract → generate — has no analog to critique for quality; it is
simply absent from the executing system, independent of whatever richness
sits unread in the YAML.

### 5.3 No self-evolution loop gated on validation performance from execution feedback — `agr optimize` is a different kind of thing entirely

This is the question the task asked to look at hardest, and the answer is
unambiguous from the source: `src/agenticgraphs/mutate.py` docstring (lines
1-6) calls the optimizer "a v0 deterministic hill-climb over safe structural
operators," explicitly contrasting it with "AFlow-style MCTS over the full
space," which it labels "future work." Concretely:

- **The operator set is fixed and non-learned** (`mutate.py` lines 131-184):
  `op_dedupe_edges` (drop literal duplicate edges), `op_parallelize_siblings`
  (mark independent siblings of a single parent as a `parallel_group`),
  `op_tighten_max_steps` (shrink `termination.max_steps` toward
  `2 × observed_worst_case_steps` — but *only* if `profile.json`'s cached
  `measured.pass_rate == 1.0`, i.e. it will not touch a graph with any
  recorded failure). None of these read a single trajectory, a success/
  failure contrast, or any content of what a model did — they operate on the
  static YAML topology and one cached aggregate number. There is no LLM
  refiner call anywhere in this code path.
- **The acceptance gate is "doesn't break the fixtures," not "beats the
  current score on held-out data."** `optimize()` (lines 187-210) calls
  `_cases_still_pass(name, doc)` (lines 39-57), which replays the graph's own
  `cases.yaml` golden cases through a `MockRunner` — scripted node outputs
  authored alongside the graph, not live model behavior, and not an
  independently sampled validation split distinct from what informed the
  graph's own authoring. An operator that regresses a golden case is
  reverted (`doc = yaml.safe_load(before)`); one that doesn't is kept. This
  is much closer to "don't regress the unit tests" than to the paper's
  `S_val(cand) ≥ S_val(current)` measured against data the mutation never
  saw.
- **No rejection memory in the paper's sense.** `lineage.yaml` (example:
  `graphs/software-engineering/code-review-pipeline/lineage.yaml`) only ever
  logs *accepted* mutations — `infuse`/`optimize` entries with a timestamp and
  what changed. There is no object anywhere in the codebase analogous to
  `H_rejected`: no log of rejected candidates, no attached trajectories, no
  attached validation scores, and therefore nothing available to feed back
  as "don't try this again" context into a future mutation proposal (there is
  no future mutation *proposal* step to feed it into in the first place,
  since the operators are fixed code, not generated by an LLM reading
  context).
- **`agr infuse` (human- or agent-invoked ability addition) is a different
  operation from either of the above** — it adds one ability string to one
  named node on request (`mutate.py` lines 60-79), gated by schema/lint, and
  is the mechanism the README's "mutation is first-class" claim is actually
  about. It is deliberate, targeted, single-edit, and always initiated by an
  external actor (human or calling agent) naming the exact node and ability —
  not a system inferring *what* to change from diffuse trajectory evidence.

**Direct answer to the task's framing question:** graph *authoring* in
agenticgraphs today is human-or-agent-authored-then-gate-audited (README
"Contributing": "A graph is accepted when — and only when — the gate
passes"), not trajectory-driven self-evolution. The one automatic mutation
path that exists (`agr optimize`) is deterministic, structural, and
explicitly labeled by its own author-comment as a stand-in for the real
thing, not a competing design to the paper's refiner.

### 5.4 `profile.json` / evidence recordings vs. the paper's validation gate — related instinct, different mechanism and cadence

Both projects share the belief that a number must come from an actual
re-run, not a claim. But the shapes differ in ways that matter for any
adoption plan:

| | Paper's `S_val` | AGR's `profile.json` / evidence ladder |
|---|---|---|
| Computed | Automatically, every evolution round, as part of the accept/reject decision | Recorded manually/periodically (`scripts/record_live.py`), not wired into any mutation's accept/reject path |
| Split discipline | A fixed `D_val`, disjoint from `D_train` and `D_test`, defined once per benchmark (Appendix B.1) | No held-out split concept at the registry level; `cases.yaml` golden cases are typically small (1-3 per graph — README scoreboard) and are the *same* cases both `agr eval` and `agr optimize`'s regression check use |
| Consumed by a mutation gate | Yes — directly, is the gate | No — `op_tighten_max_steps` reads `profile.json`'s cached `pass_rate`, but only as a pre-condition ("don't touch if not 100%"), and no operator's acceptance depends on a fresh post-mutation measurement of it |
| Staleness handling | Not applicable — recomputed every round | Explicit and conservative: `docs/live-coverage.md` shows **all 560 pre-v1.8 recordings invalidated and excluded** after a runner/contract bug was found, with "560 recordings are held but not counted... A zero above means pending re-recording, not never measured" |
| Cross-model discipline | Reported per backbone (4 LLMs, Table 1) but the accept/reject gate itself uses only the *solver's own* backbone's score | Explicit per-model reporting with a `models_disagree` flag (`profile.json` lines 206-223) and an emoji-graded scoreboard (✅/🎲/🚫) precisely to prevent one model's pass hiding another's fail (README scoreboard section) |

The honest framing: AGR's evidence discipline is, if anything, *more* rigorous
about not letting stale or cherry-picked numbers stand — but it is a
project-wide auditing practice, not a mechanism wired into any automatic
graph-mutation decision the way `S_val` is wired into Algorithm 1.

### 5.5 Scale and node-vs-edge information asymmetry

The paper's graphs put their richness on **edges** (condition/guidance/
pitfalls) and keep node counts small (7-17, except BFCL's 131 — Appendix
B.4). AGR graphs put richness on **nodes** (`speciality`, `abilities`,
typed `inputs`/`outputs`, `kind`, `criteria` for verifiers, `retries`,
`fan_out`, `parallel_group`, `timeout_s` — `spec/agr-graph.schema.json`) and
keep graphs even smaller: "the median graph is 4 nodes" (`README.md`
Roadmap, restated in `docs/agr-v1.8.md` §"What v1.8 does not claim"). AGR's
83 graphs are explicitly framed as "motif demonstrations with real
contracts, not production workflows" (same source) — the paper's 7-27
triplet graphs (again excluding BFCL) are closer to this scale than to
anything large, but they are *task-specific procedure graphs learned/edited
from execution*, where AGR's are *hand-authored motif instances*.

## 6. Adoptable ideas, ranked

Ranked by (my judgment of) ratio of expected value to effort, most promising
first.

### 6.1 Add a `criteria`-style prose field to *edges*, not just verifier nodes
**What:** Extend the AGR graph schema with an optional per-edge `guidance`
(and optionally `condition`/`pitfalls`) string, analogous to `criteria` on
verifiers today.
**Touches:** `spec/agr-graph.schema.json` (edges block, currently `from`/
`to`/`when`/`kind` only — lines documented above), `docs/agr-v1.9.md` (new
spec doc, following the versioning convention every prior bump used),
`src/agenticgraphs/adapters.py` (carry the field into LangGraph/CrewAI/
AutoGen emission the way `criteria` was carried in v1.8), `src/agenticgraphs/
harness.py` (actually hand it to the node — see 6.2, this is a prerequisite
for that to mean anything).
**Effort:** Small-medium — schema change, one migration script akin to
`scripts/derive_criteria.py`, adapter updates. A day or two of focused work
given the precedent v1.8 already set for exactly this kind of addition.
**Worth it if:** the project decides node-level guidance (speciality
description, `prompt_seed`) is worth wiring up at all (§6.2) — an edge field
nobody reads is exactly the `prompt_seed` mistake `docs/architecture-m11.md`
§1.4 already diagnosed once ("declared, validated, and unwired... the same
shape as the gaps M8, M9 and M10 closed").

### 6.2 Wire *something* into the prompt before adding more schema — close the `prompt_seed` gap first
**What:** Before adopting any paper idea that adds new prose fields, fix the
documented pre-existing gap: make the runner actually read
`speciality.prompt_seed`, `speciality.description`, and (once added) edge
guidance, instead of the current single-sentence template
(`docs/architecture-m11.md` §1.4). This is not a paper-derived idea — it's
the project's own finding — but it is the **precondition** for #6.1 or #6.3
to have any effect, and the architecture doc already sketches the fix
(§2.3, "resolution... makes agent types real," a `ResolvedAgent` object
carrying persona + tools).
**Touches:** `src/agenticgraphs/registry.py` (resolution), `src/
agenticgraphs/harness.py` (the actual prompt-building call), possibly a new
`src/agenticgraphs/agents.py` per the architecture doc's proposed module
graph (§3 target architecture).
**Effort:** Medium — this is exactly the M-series milestone shape the
architecture doc scopes (§2.3-2.4), not a small patch.
**Worth it if:** the project wants graph-carried prose to reach models at
all — currently, per the architecture doc's own audit, it categorically
does not, for any field, on any node.

### 6.3 A bounded, *local* subgraph-serialization step for multi-node phases (not full generative guidance)
**What:** A lighter-weight version of §3.2's locate→extract→generate: for a
node inside a `kind: subgraph` composite phase, serialize its immediate
predecessors/successors (from/to edges, any new edge guidance from #6.1) into
the prompt, rather than the bare `speciality` string. Not a separate LLM
call generating advice (that's a bigger, riskier lift — see Risks, §7) — just
structured context, the "extract" step without the "generate" step.
**Touches:** `src/agenticgraphs/harness.py` (prompt assembly), `src/
agenticgraphs/subgraphs.py` (phase boundary awareness already exists here for
`maps`/`aliases` — this would reuse that machinery).
**Effort:** Small once §6.2 lands (it's the same wiring point); redundant
before it.
**Worth it if:** the efficiency ablation in the paper (§5.5, Table 3) is
taken seriously — their own data shows raw full-graph injection and
full-graph *generative* guidance both underperform a localized version on
ALFWorld, so a naive "just dump the whole graph in the prompt" approach is
explicitly the thing the paper found *not* to work. A local, structured
(not generated) version is the safer first step.

### 6.4 A held-out validation split as a first-class registry concept, reusable by `agr optimize`
**What:** Give `agr eval` a notion of a train/validation split distinct from
the single small `cases.yaml` fixture set, and make `agr optimize`'s
acceptance check compare a fresh post-mutation validation score against the
pre-mutation score (paper's Eq. 5) instead of (or in addition to) "still
passes existing fixtures."
**Touches:** `src/agenticgraphs/evalcmd.py`, `src/agenticgraphs/mutate.py`
(`_cases_still_pass` → a scored comparison), `graphs/<domain>/<name>/
cases.yaml` convention (would need a documented `split: train|val` tag or a
sibling file).
**Effort:** Medium-large — this changes what "golden case" means registry-
wide, and interacts with the small-fixture-count reality (many graphs have
only 1-2 cases — README scoreboard column "Cases"). A validation split needs
enough cases to be meaningful, which for a 1-case graph is not achievable
without authoring more.
**Worth it if:** the project decides `agr optimize` should grow beyond its
three current deterministic operators toward anything resembling learned
mutation (§6.5) — a real validation-gate mechanism is a prerequisite for
that being safe at all, not optional plumbing.

### 6.5 An LLM-proposed mutation operator, added to `OPERATORS`, gated by #6.4 — the actual self-evolution idea
**What:** A fourth operator alongside `op_dedupe_edges` / `
op_parallelize_siblings` / `op_tighten_max_steps` that reads recorded
`live/*.json` trajectories (both passing and failing, which already exist
per-graph — README scoreboard "Live (real model)" column) and proposes
add/delete edits the way the paper's refiner does, still going through the
existing `_write_checked` schema+lint gate and (with #6.4) a held-out score
comparison.
**Touches:** `src/agenticgraphs/mutate.py` (new operator), a new refiner
prompt (structurally similar to the paper's Appendix B.5 template, adapted
to AGR's YAML shape), `docs/autonomy.md` (this is exactly the kind of change
that should stay behind `AGR_AUTONOMOUS` + `auto/mutations`, never direct-
to-`main`, per the existing autonomy philosophy).
**Effort:** Large. This is the actual paper-equivalent feature, and it is
appropriately last on this list — everything above it is a precondition
(structured edge guidance to mutate meaningfully, a real validation gate to
mutate safely, prompt wiring to make any of it observable in behavior).
**Worth it if:** #6.1-#6.4 land and prove out, *and* the project is willing
to accept the failure modes in §7 (this is the item those risks are mainly
about) — I would not start here.

### 6.6 Rejection memory as a lineage extension
**What:** Extend `lineage.yaml` to optionally record *rejected* mutation
attempts (from #6.5, once it exists) alongside accepted ones, so a future
refiner call can be given "don't try this again" context the way the paper's
`H_rejected` works.
**Touches:** `src/agenticgraphs/mutate.py` (`_lineage_append` already exists
and takes an arbitrary dict — this is close to free once #6.5 exists to
generate rejected candidates worth logging).
**Effort:** Small, but has no value in isolation — strictly downstream of
#6.5.
**Worth it if:** #6.5 ships and repeated-failed-proposal loops turn out to
be a real problem in practice (the paper found this worth building a whole
mechanism for — Appendix E.2 shows rounds 3/4/6 all being rolled back on
EnterpriseArena, suggesting the refiner does repeat unsuccessful directions
without it).

### 6.7 Adopt the paper's "accept ties" rule and its stated caveat about small validation sets, verbatim, as documented policy
**What:** Not code — a documentation decision. If/when #6.4 or #6.5 land,
explicitly decide and record (in `docs/agr-v1.9.md` or similar) whether ties
are accepted (paper's choice, arguably reasonable to prevent stagnation) and
explicitly state the statistical caveat the paper itself states: with a small
validation set, accept/reject decisions "turn on one or two episodes" and
should be read as a search trace, not a significance test.
**Touches:** Documentation only, once the mechanism exists.
**Effort:** Trivial.
**Worth it if:** #6.4/#6.5 ship — cheap insurance against overclaiming
significance the project doesn't have, consistent with agenticgraphs'
existing "quality is measured not claimed" ethos (README) and its own
history of walking back overclaimed evidence (`docs/evidence-history.md`).

## 7. Risks and reasons not to adopt (or to adopt cautiously)

**The paper's own loop has no isolation branch, and that is a real
difference in blast radius, not a cosmetic one.** Algorithm 1 commits an
accepted candidate directly as the new `G_k` — there is no equivalent of
`auto/mutations`, no "never `main`, never pushed" rule (`docs/autonomy.md`).
If agenticgraphs adopts a trajectory-driven refiner (§6.5), the existing
autonomy isolation model is the thing that makes it safe to try at all — it
should not be weakened or bypassed to make the feature feel more like the
paper's fully-automatic version. Keep the isolation; do not import the
paper's lack of it.

**Overfitting to a validation set is a documented failure mode in the paper
itself, not a hypothetical.** Round 10 of the EnterpriseArena trace (Table
11, §5.4) shows exactly this: 90.0% training-set survival that did not
transfer to validation (85.0%, a regression), caught only because the gate
existed. If AGR adopts a validation-gated operator (§6.4/6.5) without enough
held-out cases per graph, the gate itself becomes noise — the paper's own
caveat about "one or two episodes" deciding an accept/reject applies with
even more force to AGR graphs that currently ship with 1-2 total golden
cases (README scoreboard "Cases" column, many graphs). **A validation gate
on too few cases is worse than no gate, because it manufactures false
confidence** — this is the sharpest version of the risk, and it is a direct
consequence of AGR's current small-fixture-count reality, not a generic
warning.

**Drift and silent topology regression are exactly what `_lint_motif`,
`_lint_flow_keys`, and the provenance rule in v1.8 already exist to catch
for *human*-authored changes** (`docs/agr-v1.8.md`) — but those lints check
structural/self-grading properties, not semantic drift ("does this graph
still do what its `usecase.yaml` says it does"). An LLM refiner mutating
topology under time pressure to satisfy a validation score could produce a
graph that passes every existing lint and beats its validation score while
drifting away from its documented use case — the paper's own Round 8
"administrative bypass" edit (replacing a `fund_raising_request→book_closing`
edge with a direct edge to `End`) is a good example of a change that is
locally justified by measured improvement but is the kind of edit a human
reviewer would want to sanity-check against intent, not just against a
score. AGR's evidence discipline (CARD.md, `usecase.yaml`) gives it more to
check drift *against* than the paper's Algorithm 1 has, but nothing in the
current codebase automatically checks a mutation against its stated
use-case description — that would need to be built alongside §6.5, not
assumed to come for free from existing lints.

**The paper's guidance model runs a generation call every step, and the
paper's own numbers show this is not free.** Table 3: full-graph generative
guidance costs 96,360 tokens/sample on ALFWorld vs. 18,055 for the no-graph
baseline — over 5×. Even the paper's *preferred* localized-generative
configuration still costs 28,064 vs. 18,055 (+55%). Before adopting any
generative-guidance step (§6.3, and especially any future step toward full
§3.2), agenticgraphs should weigh this against its own stated concern for
being a lightweight, portable registry — a registry whose graphs are
intentionally 4 nodes median is a different cost profile than the paper's
task-specific, execution-tuned graphs, and a naive per-step guidance call
could dominate the cost of small AGR graphs disproportionately.

**Import bias risk: the paper evaluates itself, and it evaluates favorably.**
This document should not be read as independent confirmation that the
mechanism works well in general — it's one paper's benchmarks, on backbones
current as of the paper's writing, with baselines the authors selected and
implemented themselves (Appendix B.3 states baselines were adapted by the
paper's authors, using the same training trajectories). The 19-wins/2-ties/
3-losses record, while a real result with a reported significance test, is
not evidence about how a similarly-shaped mechanism would perform bolted
onto AGR's very differently-scoped graphs (4-node motif demonstrations vs.
task-specific 7-27-triplet procedure graphs tuned on the task's own
training data).

## 8. Open questions

**For the paper's authors:**
1. Is the four-relation vocabulary (`LEADS_TO`, `TRIGGERS`,
   `PROVIDES_INPUT_FOR`, `CONVERGES_TO`) fixed by the framework, or did it
   simply happen to be sufficient for these seven benchmarks? The paper
   states these are the types that occur (Appendix B.4) but does not state
   whether the refiner is constrained to this vocabulary or free to invent
   new relation labels — this materially affects whether "relation" is a
   controlled taxonomy or an open string.
2. What happens when the guidance LLM's neighborhood-reading step
   disagrees with — or contradicts — the solver's own reasoning? The paper
   frames guidance as a "soft bias" but doesn't report how often the solver
   ignores it, or whether ignored guidance is itself a signal fed back into
   the refiner.
3. Given Round 10's rollback (training up, validation down) and the paper's
   own honest note about small-validation-set power, how sensitive is the
   *final returned graph* (not just individual round decisions) to the
   validation split's random seed? Not stated in retrieved sources whether
   this was tested.
4. The paper reports the guidance/refiner model always shares the solver's
   backbone — is there any reason to expect a *cheaper* guidance/refiner
   model (paired with a stronger solver) would work, given that the
   guidance task is arguably simpler (translate structure to text) than the
   solving task?

**For agenticgraphs itself:**
1. Given `docs/architecture-m11.md`'s finding that graph-carried prose
   (`prompt_seed`, descriptions) reaches zero lines of runtime code today,
   is closing that gap (§6.2) actually a prerequisite the project intends to
   pursue, or is the registry deliberately staying "graph-as-config" and
   leaving prompt construction to whatever harness a downstream user brings?
   This materially changes whether §6.1/6.3 are worth doing at all.
2. Does the project want AGR graphs to remain small, hand-authored motif
   demonstrations indefinitely (as `docs/agr-v1.8.md`'s "What v1.8 does not
   claim" section currently frames them), or is there an intended future
   where graphs grow into the paper's kind of task-specific, execution-tuned
   artifact? The adoption ranking in §6 assumes the latter is at least being
   considered; if not, most of §6.4-6.6 has no motivating use case.
3. If a validation-gated mutation operator (§6.4/6.5) is built, should it
   apply to the registry's *shared* graphs (raising the "overfitting to
   whichever team authored the validation cases" risk across all
   consumers), or should validation-gated evolution be scoped per-deployment
   (a user's own fork evolves its own copy against its own data, never
   merged back)? The paper's setting (one team, one benchmark, one graph)
   doesn't have this multi-tenant question at all.
